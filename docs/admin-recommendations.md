# Админка для лендингов Balance Pay

Документ для человека, который будет выбирать, откуда сайт берёт тексты, медиа и меню. Это сравнение вариантов под текущее устройство проекта, а не план внедрения.

Сайт — Next.js (App Router). Страница — это JSON: `meta` и массив `sections[]`. У каждой секции есть `type`, и этот тип связан с компонентом и zod-схемой в `src/components/sections`. Чтение идёт только через `src/lib/content.ts` (`getPage`, `getNav`, `getCommon`, `getCollection`, `getEntry`). Сейчас источник — файлы `content/ru/**`. В `content.ts` уже отмечено, что позже чтение файлов может смениться на запрос к API с `revalidate`, без переписывания секций. Контент, который не проходит схему, на сайт не попадает: это проверяет `npm run content:check`.

От админки здесь нужен не свободный конструктор страниц. Вёрстка секций зафиксирована по макетам. Редактор меняет тексты, ссылки, медиа и состав уже существующих блоков. Новая вёрстка по-прежнему появляется в коде, вместе со схемой.

Ниже четыре варианта, которые ложатся на этот контракт по-разному.

## 1. Своя админка поверх текущего JSON

Отдельные экраны в этом же приложении (или рядом), которые редактируют те же сущности: страница, секция известного типа, меню, общие строки, коллекции. Формы можно собирать из тех же zod-схем, что уже проверяют файлы. Сохранённый документ остаётся в форме, которую сайт уже умеет читать. Публикация — запись в текущие JSON (через git) или отдача того же JSON по API, который потом подставит `content.ts`.

Такой вариант ближе всего к тому, как проект устроен сейчас. Редактор не может сохранить секцию неизвестного типа или поле, которого нет в схеме. Превью — это сам сайт. Медиа остаются файлами в `public/`, пока для них не появится отдельное хранилище.

Своя админка — это свой объём: роли, черновики, история, загрузка картинок, несколько редакторов одновременно. Пока контент ведут разработчики или один маркетолог, этого объёма можно не делать. Когда редакторов становится несколько и им нельзя давать репозиторий, объём становится основным.

## 2. Strapi

Strapi — отдельный Node-сервис со своей базой, ролями, медиатекой и i18n. Страницу можно описать как запись с dynamic zone: каждый `type` секции — компонент Strapi с теми же полями, что в zod.

Редактору так удобно: списки, черновики, права, загрузка файлов из коробки. Для этого проекта цена в другом месте. Ответ Strapi — не тот JSON, который уже лежит в `content/ru` и который проверяет сайт. Между Strapi и `getPage` нужен слой, который собирает ответ обратно в `meta` + `sections[]` и прогоняет его через те же схемы. Поля придётся держать в двух местах: схема компонента Strapi и zod. Если они разъедутся, страница либо не соберётся, либо редактор сохранит то, что сайт отбросит.

Strapi уместен, если админку делает отдельная команда, редакторам нужна привычная CMS, а трансформация в текущий контракт — осознанная часть работы. Для лендинга с жёсткими секциями это более тяжёлый контур, чем объём самого контента.

## 3. Payload

Payload ставится рядом с Next.js или внутри него. Контент описывается блоками, и блок хорошо совпадает с секцией: у блока есть имя и поля, страница — список блоков. Черновики, версии, роли и загрузка медиа входят в продукт. Публикация может отдавать JSON, близкий к нынешнему `sections[]`, и дергать вебхук ревалидации.

Схема всё равно живёт второй раз — в конфиге Payload, а не только в zod. Её можно генерировать из zod или проверять ответ Payload теми же схемами перед отдачей на страницу. Это меньше инфраструктуры, чем отдельный Strapi с Postgres, и меньше своего кода, чем админка с нуля. Редактор работает в интерфейсе Payload, а не в форме, собранной специально под эти лендинги.

Payload подходит, если нужен готовый редактор и при этом хочется остаться в одном TypeScript-проекте, не вводя второй сервис с другим форматом ответа.

## 4. Редактор файлов в git (Keystatic, Tina, Decap)

Эти инструменты редактируют файлы репозитория: JSON или Markdown — и публикуют коммитом. Для текущего `content/ru` это самый короткий путь: документ страницы уже является источником правды, превью — ветка или черновик в git, схема может остаться zod.

Слабее сторона — люди, которые не работают с репозиторием. Права, медиа и одновременное редактирование здесь слабее, чем у Strapi или Payload. Для одного-двух человек, которые и так выкладывают тексты в git, этого часто достаточно. Для отдела маркетинга без доступа к репозиторию — нет.

## Как они соотносятся

| | Своя админка | Strapi | Payload | Редактор в git |
|---|---|---|---|---|
| Совпадает с текущим JSON и zod | да, если формы из схем | только после преобразования | близко, если ответ проверять схемами | да |
| Отдельный сервис и база | нет | да | нет или рядом с Next | нет |
| Редактор без репозитория | да | да | да | слабо |
| Черновики, роли, медиатека | писать самим | есть | есть | ограничены |
| Риск разъехаться с вёрсткой секций | низкий | средний: две схемы | средний: две схемы | низкий |

Для этого сайта важнее сохранить контракт `sections[]` и zod, чем получить универсальную CMS. Своя админка и редактор файлов в git этот контракт не подменяют. Payload его повторяет блоками внутри того же приложения. Strapi его закрывает динамическими зонами, но ответ всё равно придётся приводить к формату, который уже читает `content.ts`.

Если контент по-прежнему будут менять те, кто выкладывает сайт, ближе редактор файлов или тонкая своя форма поверх JSON. Если контент уходит людям без репозитория и им нужны роли, черновики и загрузка картинок, ближе Payload: один TypeScript-контур и блоки вместо отдельной модели. Strapi имеет смысл, когда админку сознательно отделяют от сайта и готовы поддерживать преобразование в текущий JSON.
